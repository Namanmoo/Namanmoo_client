# 나만무(NaManMoo) — 본개발 기능 명세서 (AI 프롬프팅 기반 재구성)

- 문서 목적: 해커톤 제출용. 본개발 과정에서 AI 코딩 어시스턴트(Claude Code)에 입력한 약 300건의 프롬프트(2026-07-29 ~ 2026-08-09)를 역산하여, 실제 구현된 기능을 **하나의 명세서 형태**로 재구성한 것이다. 각 요구사항은 실제 프롬프트로 지시·검증된 내용이다.
- 상위 문서: 프로토타입(AIGame/DrawRaid) `요구사항명세서.md` v1.0, `기술설계서.md` v1.0, `프로토타입-프롬프팅-정리.md`
- 프로젝트: 플레이어가 직접 그린 그림을 AI가 무기로 변환하는 2D 탑다운 로그라이크 (Unity WebGL 클라이언트 + 백엔드 서버)

---

## 1. 문서 개요

### 1.1 프로토타입과의 관계

프로토타입(DrawRaid)에서 "그린 그림 → AI 무기 변환" 핵심 루프와 효과 블록·버젯 아키텍처를 검증한 뒤, 본개발에서는 검증된 파이프라인을 새 클라이언트에 이식하고 로그라이크 던전·사운드·BGM·무기 장착 애니메이션을 신규 구축했다.

### 1.2 프로토타입 대비 주요 변경 결정

| 항목 | 프로토타입 | 본개발 결정 | 결정 경위(프롬프트) |
|---|---|---|---|
| 게임 구조 | 1~4인 협동 보스 러시 | 룸 기반 로그라이크 던전 | "바인딩 오브 아이작을 참고한 랜덤 맵" 설계 논의 |
| 드로잉 도구 | HTML 캔버스 하이브리드(프로토 한정) | **Unity 네이티브 드로잉** — 기술설계서 §4.1의 본개발 전환 계획 이행 | AIGame 도구 구성을 참고하여 재구현 지시 |
| AI 이미지 개입 | 누끼(배경 제거)만, 생성형 변형 금지 | **개입 단계 슬라이더 3단계** 신설 (원본 유지 원칙은 0단계로 보존) | "1단계 개입 없음, 2단계 형태 유지 개선, 3단계 전면 재디자인" |
| 배경 제거 | rembg 서버 컨테이너 | 클라이언트 플러드 필 (흰 배경 키잉) | 경량화. 한계 확인 후 rembg는 향후 과제로 기록 |
| 이미지 생성 API | 없음 | Gemini 이미지 모델 (Cloudflare Workers AI와 비용 비교 후) | 뉴런 소모량·일일 한도 비교 질의 |
| 사운드/BGM | 최소 SFX 세트 | 속성 태그 컨벤션 기반 SFX 시스템 + 자체 작곡 BGM | §6, §7 |

### 1.3 용어

| 용어 | 정의 |
|---|---|
| 개입 단계 | 무기 그림에 대한 AI 이미지 처리 수준. 0(그대로) / 1(형태 유지 개선) / 2(전면 재디자인) |
| 무기 카탈로그 | 무기가 가질 수 있는 분류×궤도×효과의 전체 조합 명세(JSON). 백엔드가 원본, 클라이언트는 동기화 사본 |
| 그립/탑 | 무기 그림에서 사용자가 지정하는 손잡이 좌표(그립)와 무기 끝 좌표(탑). 장착·애니메이션의 기준점 |
| 핸드 리그 | 캐릭터 애니메이션 프레임마다 무기의 위치·회전을 정의하는 리그. 그립·탑 좌표에 정렬된다 |
| 속성 태그 | 효과음 파일을 동작(motion)×무게(weight)×재질(material) 조합으로 명명하는 컨벤션 |
| 폴백 사운드 | 정확한 태그 조합의 파일이 없을 때 대체 재생되는 상위 조합(`any`) 사운드 |

## 2. 핵심 게임 루프

```
[타이틀] ─ BGM 자동 재생(브라우저 상호작용 정책 준수)
   ↓
[무기 만들기] ─ 드로잉 → 추가 설명(선택) → 개입 단계 선택 → AI 처리
   │            → 결과 확인(이걸로 하기 / 다시 그리기) → 무기고 저장
   ↓
[던전(Stage)] ─ 룸 클리어 → 문 개방 → 다음 룸 (미니맵 갱신)
   │            보스 룸 → 보스 2페이즈 전투 → 스테이지 클리어 화면
   ↓
[결과/반복]
```

**FR-LOOP-01** 게임 흐름은 "게임 시작 → 무기 만들기 → 게임 진행"으로 구성한다.

**FR-LOOP-02** 무기 만들기 화면에서 무기고를 열어 기존 무기를 장착하고 바로 입장할 수 있다.

**FR-LOOP-03 (비차단 원칙)** 백엔드 장애·AI 실패·저장 실패가 게임 진행을 막아서는 안 된다. 실패 시 "그대로" 버전과 기본 스탯으로 폴백하고 경고만 남긴다. (프로토타입 NFR-03 계승)

## 3. 무기 생성 시스템

### 3.1 드로잉 도구 (Unity 네이티브)

**FR-DR-01** 드로잉 캔버스는 다음 도구를 제공한다: 연필·크레용·지우개, 기본 4색 + 확장 팔레트 12색, **색 채우기(버킷)**, 되돌리기/다시하기(20단계). AIGame 프로토타입의 도구 구성과 동일 수준을 목표로 한다.

**FR-DR-02** 색 채우기는 스캔라인 플러드 필로 구현하고, 손그림 외곽선의 안티에일리어싱을 고려해 허용 오차를 둔다.

**FR-DR-03** 그리기 텍스처는 투명 배경으로 유지한다. 내보낸 PNG의 알파 채널이 그대로 인게임 스프라이트가 된다.

**FR-DR-04** 설명 텍스트는 선택 입력이다. 입력하지 않아도 무기 생성이 가능해야 한다.

**FR-DR-05 (한글 입력)** WebGL 환경의 한글 IME 문제는 외부 패키지(WebGLInput) 의존 대신 **직접 구현**으로 해결한다. 한글 폰트는 OS 폰트를 쓸 수 없으므로 OFL 폰트(Gaegu)를 프로젝트에 포함한다.

### 3.2 AI 이미지 파이프라인 — 개입 단계 슬라이더

**FR-AI-01** 플레이어는 슬라이더로 AI 개입 단계를 선택한다.

| 단계 | 결과물 | 처리 위치 |
|---|---|---|
| 0. 그대로 | 그린 그림 원본 | 클라이언트 (이미지 API 호출 없음) |
| 1. 조금 멋있게 | 형태 유지, 선·색만 정리 | 백엔드 → Gemini 이미지 모델 |
| 2. 완전 멋있게 | 컨셉만 살린 새 무기 아트 | 백엔드 → Gemini 이미지 모델 |

**FR-AI-02 (비용 통제)** 선택한 단계만 생성한다 — 이미지 API 호출은 무기당 최대 1회, 0단계는 0회. API 선정은 무료 한도·호출당 비용(Gemini 일일 한도 vs Cloudflare Workers AI 뉴런) 비교 검토를 거친다.

**FR-AI-03** 생성 후 결과 확인 화면에서 "이걸로 하기 / 다시 그리기"를 선택한다.

**FR-AI-04** 생성 이미지의 흰 배경은 가장자리 기준 플러드 필로 제거한다. 무기 내부의 흰 하이라이트는 보존한다. (한계 시 서버 측 rembg 도입 — 향후 과제)

**FR-AI-05 (목 모드)** API 키 없이 백엔드를 실행하면 목 모드로 동작하여, 키 없이도 3버전 선택 흐름 전체를 테스트할 수 있어야 한다.

### 3.3 무기 속성 — 카탈로그 3축

**FR-WPN-01** AI는 그림과 설명을 보고 무기를 3축으로 정의한다: **분류**(근접/원거리) × **궤도**(직선·유도·부메랑·검기 등 9종) × **효과**(화염·관통·흡혈 등 10종). AI는 카탈로그 내 조합만 선택할 수 있다. (프로토타입 "효과 블록" 원칙 계승 — AI가 임의 코드를 생성하지 않는다)

**FR-WPN-02 (단일 원본)** 카탈로그는 백엔드 JSON이 원본이며 클라이언트 사본은 동기화 스크립트로 맞춘다. 양측 불일치는 패리티 테스트로 검출한다.

**FR-WPN-03 (작명)** AI가 무기 이름을 부여한다. 톤 규칙: 정성 들여 그린 무기에는 진지한 이름, 대충 그렸거나 무기가 아닌 그림에는 장난스러운 이름. 0단계(그대로)에서도 작명은 수행한다. 기본 이름은 "무기".

**FR-WPN-04 (그립·탑 지정)** 플레이어는 드로잉 화면에서 무기의 그립(손잡이)과 탑(무기 끝) 좌표를 UI로 지정·이동할 수 있다. 이 좌표는 장착·애니메이션(§5)의 기준이 된다.

### 3.4 무기고

**FR-VLT-01** 확정한 무기는 서버 무기고에 이미지 포함 저장된다. 브라우저 캐시 삭제 후에도 유지된다.

**FR-VLT-02** 무기고 화면에서 저장된 무기를 카드로 열람하고 장착·삭제할 수 있다.

**FR-VLT-03** 저장 실패 시에도 해당 판은 그대로 진행한다(FR-LOOP-03).

**FR-VLT-04 (WebGL 성능)** 카드 UI는 씬에 미리 생성해 두고 내용만 채운다. 런타임 UI 생성은 WebGL 첫 표시 지연을 유발하므로 금지.

## 4. 맵·던전 시스템

**FR-MAP-01** 맵 생성 규칙은 바인딩 오브 아이작 방식을 참고한 룸 기반 랜덤 생성으로 한다. 방 자체의 구조는 본 프로젝트의 기존 룸 구조를 유지한다.

**FR-MAP-02** 방 크기는 모두 동일하게 통일하고, 문 위치는 4방향(상·하·좌·우)으로 한다.

**FR-MAP-03** 방은 화면보다 크며 카메라가 플레이어를 따라다닌다. 카메라는 방 테두리보다 약간 넓게 보여준다.

**FR-MAP-04** 방의 적을 클리어해야 문이 열리고 다음 방으로 이동할 수 있다.

**FR-MAP-05** 미니맵을 제공한다.

**FR-MAP-06 (데이터 분배)** 전체 맵 정보는 백엔드가 보유하고, 방 이동 시 해당 방의 정보만 클라이언트에 전달한다.

**FR-MAP-07** 방 배치는 템플릿 기반으로 한다. 룸 템플릿을 에셋으로 작성·추가할 수 있어야 한다.

## 5. 무기 장착·애니메이션 (핸드 리그)

**FR-RIG-01** 캐릭터는 생성된 무기를 실제로 장착하고, AI가 정한 분류대로 동작한다 — 원거리는 그린 그림이 발사체로 날아가고, 근접은 그린 그림을 휘두른다. (프로토타입 정체성 원칙 "항상 유저가 그린 그림을 그대로 활용" 계승)

**FR-RIG-02** 무기 배치는 그립·탑 좌표(FR-WPN-04)를 기준으로 한다. 애니메이션 프레임마다 그립이 캐릭터 손 위치에, 탑이 의도한 방향에 오도록 키프레임을 정의한다.

**FR-RIG-03** 에디터에서 그립(초록)·탑(빨강) 마커를 표시하여 프레임별 배치 작업을 지원한다.

**FR-RIG-04** 공격·대기·이동 모든 상태에서 리그가 적용되어야 한다. 무기를 교체해도 동일한 리그·애니메이션이 일치되게 동작해야 한다.

**FR-RIG-05 (회전 모션)** 한 바퀴 회전 모션을 Z 회전 키프레임으로 구성한다. 키프레임 간 보간을 끊어(스텝) 손그림 애니메이션 특유의 끊기는 연출을 낼 수 있어야 한다.

**FR-RIG-06 (좌우 대칭)** 왼쪽 방향 클립은 무기 그림을 거울상으로 뒤집고, 그립·탑 좌표도 함께 반전하여 오른쪽 클립과 대칭이 되게 한다. 한쪽 방향에서 완성한 리그를 반대 방향에 재사용할 수 있어야 한다.

**FR-RIG-07 (확장 대비)** 향후 무기 타입별로 모션이 달라질 예정이므로, 모션 전환이 쉬운 구조로 코드를 준비한다(현 시점 구현은 공통 모션).

## 6. 타격 판정

**FR-HIT-01** 근접 무기의 판정 범위는 **그린 무기 이미지와 정확히 일치**해야 한다. 이미지의 투명 영역은 판정에서 제외하고 무기 픽셀만 사용한다.

**FR-HIT-02** 피해는 무기 에셋이 대상과 실제로 접촉하는 순간 적용한다. 접촉 전 선판정을 금지한다.

**FR-HIT-03** 판정 규칙은 특정 몬스터가 아닌 전체 몬스터에 일관되게 적용한다.

**FR-HIT-04 (검증 방식)** 판정 수정은 정적 검증만으로 완료로 간주하지 않고, 실제 플레이 테스트(특정 무기·특정 룸 재현 조건)로 확인한다. 빌드 전 수정 내용 브리핑을 거친다.

## 7. 효과음(SFX) 시스템

### 7.1 아키텍처

**FR-SFX-01 (저장 위치)** 효과음은 클라이언트에 저장한다. 근거: 속성 태그 조합 방식(§7.2)을 쓰면 파일 수가 60개·250KB 수준으로 억제되어 런타임 배포가 불필요하다.

**FR-SFX-02 (매칭)** 무기에 어떤 소리를 붙일지는 백엔드 AI가 판단하되, 클라이언트 코드를 참조하는 것이 아니라 **사운드 태그 목록(컨벤션)** 을 기준으로 선택한다.

### 7.2 속성 태그 컨벤션

**FR-SFX-03** 효과음 파일은 `동작(motion)_무게(weight)_재질(material)` 조합으로 명명한다 (motion 5 × weight 3 × material 4 = 60조합). 런타임 피치·볼륨 랜덤화로 체감 다양성을 확보한다.

**FR-SFX-04 (임팩트)** 타격음은 "무기 재질+무게 × 대상 재질" 조합으로 구성한다. `hit`은 피격 시 재생된다(사망음과 구분).

**FR-SFX-05 (폴백 체인)** 정확한 조합 파일이 없으면 상위 조합(`any`)으로 폴백한다. 필수 폴백 파일 목록을 관리하며, 무거운 무기가 폴백 단계에서 제 소리를 잡도록 `any` 계열을 우선 확보한다.

**FR-SFX-06 (파생 생성)** 부족한 조합은 기존 파일의 재생 속도 변형으로 파생 제작할 수 있다(예: `swing_heavy` 가속 → `swing_medium`/`swing_light`).

**FR-SFX-07 (효과 카테고리)** 무기 외에 장판·상태이상용 효과음 카테고리를 둔다(예: `zone_burn_loop`).

### 7.3 리소스 워크플로·라이선스

**FR-SFX-08** 원본(freesound.org 등)은 `unfixed` 접미사로 반입하고, 노멀라이징·클리핑 등 후처리를 거친 파일을 `fixed`로 승격한다. m4a는 wav로 변환하여 적용한다.

**FR-SFX-09** 모든 외부 리소스는 파일명·출처 URL·라이선스(CC-BY 4.0 등)를 라이선스 문서에 기록한다. 반입 시 "파일명 + URL" 형식으로 등록하며, 전체 라이선스 정합성을 주기적으로 점검한다.

**FR-SFX-10** 크레딧 화면에 출처 표기를 반영한다(TODO 문서로 관리).

## 8. BGM

### 8.1 메인 테마

**FR-BGM-01** 스테이지마다 다른 곡이 재생되되, 전체를 관통하는 **메인 테마 멜로디**를 두고 각 곡은 그 변주로 만든다. 정서 방향은 "뭉클함".

**FR-BGM-02** 작곡 절차: 메인 멜로디 확정 → 조성·코드 진행 확정 → 곡별 변주 → 악기 편성. 멜로디 단계에서 악기를 논하지 않는다.

**FR-BGM-03 (확정 사항)** 조성은 E♭(F장조에서 한 키 하강). 시그니처 도약은 장6도 기반이되 부자연스러운 도약은 제거하고, 유명 코드 진행(머니코드)과 자체 진행을 혼합한다. 상성부에 B♭ 앵커를 유지해 조성감을 살린다.

**FR-BGM-04** 메인 멜로디와 어울리는 전주(인트로)를 별도 제작한다.

### 8.2 곡별 요구사항

**FR-BGM-05 (보스, 2페이즈)** 보스전은 2페이즈 구성에 맞춰 두 곡을 만든다. 기존 화성·리듬 골격에서 1페이즈는 리듬을 재구성한 버전, 2페이즈는 일렉 기타·베이스를 얹은 록 버전. 싱코페이션 수준이 아니라 리듬 자체를 바꿔 다른 곡처럼 들리게 한다.

**FR-BGM-06 (던전)** 던전 곡은 템포를 낮추고 반복 구간을 줄인다. 상행·하행 프레이즈에는 종지(마무리)를 넣는다. 장조(Major) 버전을 별도 제작하여 게임에 적용한다.

**FR-BGM-07 (필드)** 필드 곡은 MIDI 분석을 기반으로 기존 보스 테마와의 정합성을 확인한 뒤 구성한다. 일반적인 게임 BGM의 마디 수와 전체 플로우를 고려하고, "초원에서 몬스터를 사냥하는 활기찬 느낌"의 악기로 편성한다. 8비트 톤을 벗어난 악기 대체안을 검토한다.

**FR-BGM-08 (검증)** 완성곡은 청음으로 검증한다 — 조성 변환 여부, 특정 음(예: 솔♭/솔) 정확성, 베이스 라인 유무를 실제 재생으로 확인하고 불일치 시 재작업한다.

### 8.3 포맷·적용

**FR-BGM-09** 산출물은 MIDI → ogg로 렌더링하고, 필요 시 wav 버전을 추가 생성한다.

**FR-BGM-10** 완성된 음악·효과음의 게임 내 연결 지점을 목록화한 뒤 일괄 적용한다.

**FR-BGM-11 (타이틀 재생)** 타이틀 BGM은 브라우저 자동재생 정책을 준수하여 사용자 상호작용(클릭) 후 재생을 시작한다.

**FR-SYS-01** API 키는 백엔드 환경 파일에만 존재한다. 클라이언트에서 AI를 직접 호출하지 않는다. (프로토타입 NFR-04 계승)

**FR-SYS-02** 스탯 검증(클램프)은 백엔드와 클라이언트 양측에서 수행하되, 허용 범위의 원본은 카탈로그 한 곳에만 둔다.

### 9.2 빌드·테스트

**FR-BLD-01** WebGL 빌드 산출물은 로컬 포트(5173)로 서빙하여 브라우저에서 테스트한다. 브랜치 전환 시 재빌드한다.

**FR-BLD-02** 빌드 완료 확인은 자동화된 방식으로 수행한다(수동 대기 최소화).

**FR-BLD-03** 배포 서버의 압축 헤더(Content-Encoding)와 빌드 압축 설정이 일치해야 한다. wasm 스트리밍 컴파일 오류는 콘솔 로그 전문을 근거로 진단한다.

## 10. 협업·형상 관리 규칙

**FR-GIT-01** main 브랜치에 직접 커밋하지 않는다. 모든 작업은 feature 브랜치에서 수행하고 풀 리퀘스트로 병합한다.

**FR-GIT-02** 성격이 다른 작업(예: 사운드 vs 무기)은 브랜치와 커밋을 분리한다. 팀원의 미커밋 작업 영역과 겹치는 변경은 제외하고 커밋한다.

**FR-GIT-03** 병합 충돌 시 main을 기준으로 정리하고, 충돌 내용은 항목별로 리스트업하여 검토 후 해소한다.

**FR-GIT-04 (Unity 씬 병합)** `.unity` 씬 파일 충돌은 줄 단위 병합 대신, 코드 정리 후 **씬 빌더 재실행으로 씬을 재생성**하여 해소한다.

**FR-GIT-05** 테스트는 main 브랜치의 에셋을 기준으로 유지한다. 디버그 로그는 커밋 전에 제거한다.

## 12. 프롬프팅 전략 (본 명세가 도출된 방식)

본 명세의 각 요구사항은 사전에 문서로 작성된 것이 아니라, 개발 중 AI 어시스턴트와의 대화에서 결정·구현·검증된 것을 역산한 것이다. 프로토타입에서 확립한 전략(인터뷰 위임형 명세, 레퍼런스 기반 의사결정, 정체성 원칙 반복 주입)을 본개발에서도 이어가며 다음을 추가로 사용했다.

1. **선(先)비교 후(後)결정** — 저장 위치(FR-SFX-01), API 선정(FR-AI-02), 아키텍처(FR-MAP-06) 등은 구현 지시 전에 비용·트레이드오프 설명을 먼저 요청해 근거를 확보한 뒤 결정했다. ("우선 수정하지 말고 제안해 주세요.")
2. **단계적 구체화** — 큰 기능(BGM, 핸드 리그)을 설계 논의 → 방식 결정 → 구현 → 검증으로 나누어 프롬프트를 진행했다. BGM은 멜로디 → 조성 → 변주 → 악기 순으로 단계를 강제했다(FR-BGM-02).
3. **도메인 지식 기반 반복 피드백** — 조성·코드 진행·도약 음정 등 음악 이론 용어로 피드백을 반복하고, 청음 결과와 AI의 주장이 다르면 재검증을 요구했다(FR-BGM-08).
4. **실측 데이터 기반 디버깅** — 오류는 추측 대신 브라우저 콘솔 로그 전문과 재현 조건(사용 무기·테스트 룸)을 전달했다(FR-BLD-03, FR-HIT-04).
5. **작업 범위의 명시적 제한** — "코드는 수정하지 말고 컨벤션만", "무기 작업은 제외하고 사운드만"처럼 변경 범위를 프롬프트에 명시해 협업 충돌과 의도치 않은 수정을 방지했다(FR-GIT-02).
6. **AI 보고의 실기 검증** — AI의 완료 보고를 그대로 수용하지 않고 플레이 테스트로 대조하여 재작업을 요구했으며, 빌드 전 수정 내용 브리핑을 관행화했다(FR-HIT-04).
